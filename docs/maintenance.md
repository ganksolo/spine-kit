# 版本、升级、恢复与维护

VERSION 使用语义版本：breaking 流程/配置变化升 major；兼容能力升 minor；修复/文档纠正升 patch。
0.x 阶段仍必须在 CHANGELOG 明确不兼容变化。版本字符串不能替代内容 hash / Git commit。
发布 tag 只在实际创建后才称已发布；本地 VERSION 不代表远端已有对应 tag。

## 项目升级

1. 保留当前 manifest、vendor、项目配置和本地适配；查看未提交修改。
2. 读取新版本 CHANGELOG 与迁移说明，选择固定 commit。
3. 在隔离分支比较“旧 vendor / 新源 / 项目适配”三方；保留项目规则与任务事实。
4. 手动更新所需快照和配置、来源摘要，或在临时副本重新 setup 后审查差异；不删除 `.spine` 后盲目重装。
5. 重跑 validate / verify，更新 report 并 finalize；记录升级日志和遗留问题。

0.1.0 不提供自动升级；不要绕过 bundle 不匹配检查强行 apply。执行者必须理解 vendor hash 与 manifest 的对应关系。
优先固定工作流版本；第三方技能单独记录版本与安装方式，不把“插件自动更新”当兼容保证。

## 撤销 / 中断

apply 的日志记录每次创建的相对路径与 hash；从 Git diff 和日志确定影响范围。
只删除确认由此次创建且 hash 仍匹配的文件；已改动文件保留并手动合并。
不使用全目录 rm、不 git reset 用户已有改动、不清理未知未跟踪文件。
manifest 缺失但存在部分 vendor 时，同一 bundle 可重跑补齐；vendor 内容冲突时停止并核实来源。
保留 setup 日志用于追溯（人工处理前先备份日志）。并发写入目标不受支持。

## 文档维护

一个事实一个权威位置：产品约束在 Spine；任务进度在任务源；接续指针在 context；历史在 journal/归档；
架构决策在 ADR。AGENTS/CLAUDE 只保留入口与稳定规则，不复制进度。
按任务/时间归档长 journal，保留索引和证据链接。不要为了缩短文件而销毁诊断信息。

## 仓库发布检查

运行单元测试、检查 Markdown 链接、用全新和已有临时项目验证 setup，并审查无秘密或业务数据。
记录独立 Review 和真实项目试点状态；未完成不能隐去。跨项目反馈只接收脱敏的最小案例。
